# 주문 상세

진입 경로: 대시보드 > pre-order > 주문 조회 > 주문 상세

---

- 주문 조회 범위와 역할별 개인정보 표시는 [권한 및 조회 범위 정책](../policy/Policy_02_권한_및_조회_범위.md)을 따른다. 아래 개인정보 표시 기준은 대시보드 기준이며 앱 리더 모드와 구분한다.
- Hand Raiser 판정·수정 반영·인보이스 연계는 [Hand Raiser 정책](../policy/Policy_05_Hand_raiser.md#6-기존-주문의-hand-raiser-여부-수정)을, 항목별 변경 및 인보이스 재생성 기록은 [주문 이력 정책](../policy/Policy_07_주문_이력.md)을 따른다.
- 기존 주문 수정 화면에 이메일 기반 Hand Raiser 확인 기능을 추가한다. 다른 필드의 제공 여부·입력 조건·수정 가능 범위·검증은 기존 동작을 유지한다.

## 1. **주문 상세 모달**

### 1-1. **조회 모드**

- 캠페인 상세 주문 목록에서 선택한 주문의 상세 모달을 연다. 뒤의 목록은 유지하고, 모달을 닫으면 기존 목록으로 돌아간다.
- 관리자·별도 pre-order 조회 권한 리더는 기존 전체 주문 범위를 유지한다. 일반 리더는 관리 그룹·하위 그룹 구성원의 조회 가능한 주문만 상세에서 조회한다. 현재 소속 기준과 일괄 등록 제외 등은 권한 정책을 따른다.
- 기존 제목·닫기 버튼·주문 및 고객 탭 구조를 유지한다. 일반 리더의 조회 허용을 위해 별도 화면을 만들거나 고객 탭 자체를 없애지 않는다.
- 개인정보 표시와 더보기 노출은 아래 각 영역의 역할별 기준을 적용한다. 조회 허용만으로 수정·삭제·이력 조회 권한을 부여하지 않는다.

### 1-2. **수정 모드**

| 구분 | 정의 |
| --- | --- |
| Header | 기존 ‘주문 상세’ 제목을 유지한다. 수정 모드에서는 헤더 X 버튼을 표시하지 않는다. |
| Body | 기존 주문·고객 탭과 각 탭의 수정 필드를 유지한다. 고객 탭의 Hand Raiser 확인 영역을 변경한다. |
| Footer | [취소]·[저장] 버튼을 제공한다. |

- 주문 수정 진입 권한은 아래 더보기 메뉴의 기존 관리자 계열 기준을 유지한다. P07에서 리더의 수정 권한을 추가하지 않는다.
- 팝업 외부 클릭 등 기존 수정 화면의 이탈 처리는 유지한다. 이번 확인 기능으로 새 이탈 동작을 추가하지 않는다.

## 2. **주문·고객 탭**

### 2-1. **조회 모드의 정보 표시**

- 기존 주문 탭의 항목과 표시 순서를 유지한다. 고객 탭에서는 아래 세 항목의 노출 여부만 역할에 따라 구분한다.

| 역할 | 고객 전화번호·이메일 주소·신분증 번호 |
| --- | --- |
| 관리자 | 기존 표시 유지 |
| 별도 pre-order 조회 권한 리더 | 기존 표시 유지 |
| 일반 리더 | 세 항목 자체 비노출 |

- 일반 리더에게는 세 항목의 레이블·값을 모두 표시하지 않는다. 값만 마스킹하거나 빈 필드로 남기지 않는다. 전화번호에 결합된 국가번호도 함께 비노출한다.
- 이름·Hand Raiser 등 그 밖의 정보와 기존 표시 순서는 유지한다. 조회 모드의 Hand Raiser는 기존 별도 영역을 유지한다.
- 같은 주문을 조회하더라도 역할에 따라 개인정보 표시가 달라진다. 상세 조회 범위 자체는 1-1의 기준을 따른다.

### 2-2. **수정 모드의 탭 동작**

| 케이스 | 조건 | 명세 |
| --- | --- | --- |
| Case 2-1 | 주문 상세에서 수정 진입 | <ul><li>현재 선택한 주문·고객 탭을 유지한다.</li><li>기존 주문 데이터를 수정 필드에 표시한다.</li></ul> |
| Case 2-2 | 수정 중 탭 전환 | <ul><li>입력 중인 값과 Hand Raiser 확인 상태를 유지한다.</li><li>고객 탭에서 재검증이 필요한 상태라면 주문 탭에서도 [저장]을 비활성화한다.</li></ul> |

## 3. **더보기 메뉴**

- 기존 주문 상세의 더보기 메뉴에 [이력]을 추가한다. 메뉴 순서는 [이력] → [수정] → [삭제]다.
- 기존 [수정]·[삭제] 메뉴의 권한·동작은 유지한다. 현재 대시보드의 더보기는 관리자 계열(ADMIN·SUPER_ADMIN·OPERATOR)에만 노출되며, 리더는 pre-order 조회 권한이 있어도 수정·삭제 메뉴를 제공하지 않는다. 신규 [이력]도 동일한 관리자 계열 기준을 따른다.

| 역할 | 더보기 버튼·메뉴 |
| --- | --- |
| 관리자 계열(ADMIN·SUPER_ADMIN·OPERATOR) | 표시. [이력] → [수정] → [삭제] 순서 |
| 별도 pre-order 조회 권한 리더 | 버튼과 메뉴 모두 비노출 |
| 일반 리더 | 버튼과 메뉴 모두 비노출 |

### 3-1. **이력 메뉴 항목**

| 케이스 | 조건 | 명세 |
| --- | --- | --- |
| Case 3-1-1 | 관리자 계열 | <ul><li>[이력] 메뉴를 표시한다.</li><li>[이력] 선택 : 기존 주문 상세를 유지하고 그 위에 현재 주문의 주문 이력 모달을 연다.</li></ul> |
| Case 3-1-2 | 리더 | <ul><li>별도 pre-order 조회 권한 유무와 관계없이 더보기 메뉴([이력]·[수정]·[삭제])를 표시하지 않는다.</li><li>주문 상세의 다른 정보·동작은 각 조회 권한 정책을 따른다.</li></ul> |

- 기록이 없는 기존 주문도 [이력] 메뉴는 표시한다. 조회 결과가 없는 경우 [주문 이력](Web_dc_02_주문_이력.md)의 빈 상태를 적용한다.
- 기능 적용 이후의 기록 대상과 보관 기준은 [주문 이력 정책](../policy/Policy_07_주문_이력.md)을 따른다.

- 이력 모달을 닫으면 뒤에 유지된 기존 주문 상세가 다시 보인다. 주문 상세의 조회 상태를 초기화하지 않는다.

### 3-2. **수정 메뉴 항목**

- 기존 [수정] 선택 시 현재 선택한 주문·고객 탭을 유지하고 수정 모드로 진입한다.
- 이메일 아래 Hand Raiser 확인 기능과 수정 저장 조건은 아래 고객 정보 입력 영역 및 하단 버튼 영역을 따른다. 조회 모드의 기존 별도 Hand Raiser 영역은 유지한다.

## 4. **고객 정보 입력 영역**

- 기존 이름·휴대폰 번호·이메일·신분증 번호 및 그 밖의 고객 정보 필드는 기존 순서와 수정 조건을 유지한다.
- 주문 상세 조회 모드의 별도 Hand Raiser 영역은 유지한다. 수정 모드에서는 별도 영역 대신 이메일 필드 바로 아래에 Hand Raiser 여부 확인 기능을 제공한다.

### 4-1. **이메일 필드**

| 케이스 | 조건 | 명세 |
| --- | --- | --- |
| Case 4-1-1 | 수정 최초 진입 | <ul><li>주문에 저장된 이메일을 표시한다.</li><li>이메일의 필수·형식 검증은 기존 기준을 유지한다.</li></ul> |
| Case 4-1-2 | 이메일 변경 | <ul><li>기존 Hand Raiser 확인 결과를 해제한다.</li><li>아래 확인 영역을 [확인] 버튼 상태로 바꾸고 [저장]을 비활성화한다.</li><li>이 상태에서는 재검증이 필요하다. 재검증 전에는 주문 수정을 저장할 수 없다.</li></ul> |

- 재검증 대상은 이 필드의 현재 입력값이다. 기존 저장 이메일이나 이전 입력값의 확인 결과를 새 이메일에 사용하지 않는다. 비동기 조회 응답과 현재 입력값을 연결하는 처리는 개발 시 확인한다.

### 4-2. **Hand Raiser 확인 영역**

- 이메일 필드 아래의 한 영역 안에 왼쪽 ‘Hand raiser 고객 여부’, 오른쪽 확인 상태 또는 버튼을 배치한다.
- Yes/No를 직접 선택하는 토글·선택 메뉴는 제공하지 않는다.

#### 4-2-1. **확인 결과 표시**

| 케이스 | 조건 | 명세 |
| --- | --- | --- |
| Case 4-2-1-1 | 수정 최초 진입 | <ul><li>오른쪽에 주문의 기존 Yes/No와 초기화 아이콘 버튼을 표시한다.</li><li>진입만으로 현재 명단을 조회하지 않는다.</li></ul> |
| Case 4-2-1-2 | 명단 확인 완료 | <ul><li>현재 입력한 이메일이 해당 주문의 캠페인 명단에 있으면 Yes, 없으면 No를 표시한다.</li><li>결과 오른쪽에 초기화 아이콘 버튼을 표시한다.</li><li>No도 정상 확인 결과로 처리한다. Yes가 아니라는 이유로 저장을 막지 않는다.</li></ul> |
| Case 4-2-1-3 | 초기화 또는 이메일 변경 | <ul><li>Yes/No와 초기화 아이콘 대신 [확인] 버튼을 표시한다.</li></ul> |

#### 4-2-2. **초기화 아이콘 버튼**

- 현재 화면의 Hand Raiser 확인 결과를 해제하고 [확인] 버튼을 표시한다. 이메일 입력값은 유지한다.
- 재검증 전까지 [저장]을 비활성화한다. 저장된 주문의 여부를 즉시 변경하거나 명단에서 이메일을 삭제하지 않는다.
- 이메일이 동일하더라도 초기화 후 다시 확인하여 현재 명단 기준으로 여부를 갱신할 수 있다.

#### 4-2-3. **확인 버튼**

| 케이스 | 조건 | 명세 |
| --- | --- | --- |
| Case 4-2-3-1 | 재검증 필요 | <ul><li>현재 입력한 이메일의 기존 필수·형식 기준을 충족한 뒤 명단 확인을 요청한다.</li><li>선택한 주문이 속한 캠페인의 명단을 조회한다. 전체 명단을 화면에 불러오지 않는다.</li></ul> |
| Case 4-2-3-2 | 정상 응답 | <ul><li>등록 여부에 따라 Yes/No 결과와 초기화 아이콘을 표시한다.</li><li>화면의 확인 상태를 완료로 바꾼다. 실제 주문 값은 [저장] 성공 시 반영한다.</li></ul> |
| Case 4-2-3-3 | 응답 대기 또는 조회 실패 | <ul><li>확인 완료 전까지 [저장] 비활성을 유지한다.</li><li>조회 실패를 No 결과로 표시하지 않는다.</li><li>오류 안내·재시도 및 확인 버튼의 처리 중 표시는 기존 공통 처리와 연결하며, 사용할 API의 응답·오류 처리 방식은 개발 시 확인한다.</li></ul> |

## 5. **하단 버튼 영역**

### 5-1. **취소 버튼**

- 기존 수정 취소 확인·이탈 동작을 유지한다.
- 취소 확정 시 미저장 입력값과 재검증 결과를 폐기하고 기존 주문 상세 조회로 돌아간다. 저장된 이메일과 Hand Raiser 여부는 변경하지 않는다.

### 5-2. **저장 버튼**

| 케이스 | 조건 | 명세 |
| --- | --- | --- |
| Case 5-2-1 | 초기화·이메일 변경 후 재검증 미완료 | <ul><li>[저장]을 비활성화한다.</li><li>다른 항목을 수정했거나 주문 탭으로 전환해도 같은 제한을 적용한다.</li></ul> |
| Case 5-2-2 | 확인 완료 | <ul><li>Hand Raiser 재검증에 따른 저장 제한을 해제한다.</li><li>확인 결과가 Yes/No 어느 쪽이든 기존 변경 여부·필수값·오류 검증 등 나머지 저장 조건을 적용한다.</li><li>초기화 후 동일 값으로 다시 확인한 것만으로 실제 주문 변경이 발생한 것으로 처리하지 않는다.</li></ul> |
| Case 5-2-3 | 이메일·Hand Raiser 확인 상태를 변경하지 않음 | <ul><li>기존 저장 조건을 적용한다. 다른 정보만 수정하는 경우 Hand Raiser 재검증을 요구하지 않는다.</li><li>저장 시 기존 여부를 유지한다.</li></ul> |
| Case 5-2-4 | 저장 실행·성공 | <ul><li>기존 저장 전 검증과 확인창을 유지한다.</li><li>수정한 이메일과 확인된 여부를 다른 수정 정보와 함께 저장한다.</li><li>성공 시 주문 상세 조회로 돌아가 저장된 값을 표시한다. 조회 모드에서는 기존 별도 Hand Raiser 영역에 여부를 표시한다.</li><li>저장 성공 안내는 공통 문구 ‘저장되었습니다.’를 사용한다.</li><li>실제 여부 변경 시 정책에 따른 인보이스 재생성 조건과 주문 이력 기록을 적용한다.</li></ul> |

- 마지막 [확인] 이후 이메일이 그대로라면, 그사이 캠페인 명단이 변경됐더라도 [저장] 시 명단을 다시 조회하지 않고 마지막 [확인] 결과(Yes/No)를 저장한다.
- 저장 실패 안내·재시도는 기존 주문 수정 처리를 유지한다. 실패를 저장 완료로 표시하지 않는다.
- 인보이스 재생성·항목별 이력 기록은 [정책 7절](../policy/Policy_05_Hand_raiser.md#7-주문-수정과-인보이스이력-연계)을 따른다. 이 화면에 인보이스 재생성 버튼이나 별도 이력 화면을 추가하지 않는다.
