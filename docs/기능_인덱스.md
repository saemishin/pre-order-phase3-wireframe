# Pre-order 3차 개발 기능 인덱스

2027년 2월 캠페인에서는 더 많은 상품군을 운영하면서, 매장 직원은 취급 가능한 SKU를 주문하고 리더는 모델·색상·용량별 실적을 확인해야 한다. 고객 피드백에서 특히 강조된 부분은 관리팀이 앱에서 상품별 실적과 날짜별 추이를 함께 보는 일이었다. 캠페인을 운영하는 관리자에게는 명단을 정정하고 주문이 어떻게 바뀌었는지 추적하는 기능도 필요했다.

P01~P09에는 고객이 요청하거나 후속 대화에서 확인한 운영 배경을 담았다. P10의 세 항목은 주문·픽업 운영 검토에서 정리한 개선이다. 고객 피드백표의 P10에는 별도 답변이 없었다.

## P01 · 주문 이력 조회

주문 상세에서 현재 값만 보면 누가 어떤 정보를 고쳤는지 알기 어렵다. 고객이 원한 조회 위치는 관리자가 주문을 관리하는 웹 대시보드였다. *(고객 피드백표 G3)*

관리자는 주문 상세에서 생성·수정·픽업·삭제·복구·인보이스 재생성 이력을 시간순으로 확인한다. 한 번에 여러 항목을 고쳐도 수정자·시각·변경 전후 값은 항목별로 남긴다. 삭제와 복구도 기록 대상이지만, 삭제된 주문을 찾아 복구하는 화면은 이번 범위에서 제외했다.

**화면에서 보기**

- [주문 상세](https://saemishin.github.io/pre-order-phase3-wireframe/?scenario=P01#detail-admin) — 주문 상세의 더보기 메뉴에서 이력을 연다.
- [주문 이력](https://saemishin.github.io/pre-order-phase3-wireframe/?scenario=P01#history-list) — 최신순으로 표시된 작업 일시와 수행자를 보고, 수정된 항목의 변경 전후 값을 확인한다.
- [첨부파일 변경 예시](https://saemishin.github.io/pre-order-phase3-wireframe/?scenario=P01#history-file-add) — 첨부파일을 추가하거나 삭제한 이력에서 파일명을 확인한다. 파일 추가는 없음 → 파일명, 삭제는 파일명 → 없음으로 표시된다.
- [기록 없는 주문](https://saemishin.github.io/pre-order-phase3-wireframe/?scenario=P01#history-empty) — 기록된 이력이 없으면 빈 목록과 이력 기록 시작일 안내를 확인한다.

## P02 · 캠페인당 프로덕트 그룹 수 확대

다음 출시 캠페인에는 휴대폰 모델과 웨어러블 등 함께 운영할 상품군이 늘어난다. 고객은 기존 5개로는 그룹이 부족해 최소 10개를 요청했고, 20개로 확대하는 안이면 충분하다고 답했다. RAM·저장 용량·색상 조합으로 구성하는 그룹 안의 SKU 수는 현재 수준으로 충분하다는 답변도 받았다. *(고객 피드백표 F4:G4)*

한 캠페인에 최대 20개 그룹을 설정한다. 관리자는 Product에서 그룹별 상품을, Allocation에서 각 그룹의 배정 수량을 관리한다. 그룹을 오가도 작성 중인 입력은 유지된다.

**화면에서 보기**

- [Product · 그룹 설정](https://saemishin.github.io/pre-order-phase3-wireframe/?scenario=P02#product-basic) — Product 단계에서 그룹을 추가하고 이름과 상품 정보를 입력한다. 탭을 선택해 다른 그룹으로 이동하거나 해당 그룹을 삭제한다.
- [Product · 최대 20개](https://saemishin.github.io/pre-order-phase3-wireframe/?scenario=P02#product-many) — 탭이 화면 너비를 넘으면 좌우로 이동해 그룹을 선택한다. 그룹이 20개가 되면 추가 버튼이 비활성화된다.
- [Allocation · 수량 배정](https://saemishin.github.io/pre-order-phase3-wireframe/?scenario=P02#allocation-basic) — Allocation 단계에서 캠페인 전체의 배정 파일을 업로드하고, 그룹별 탭에서 배정 수량을 확인한다.

## P03 · 프로덕트 그룹·SKU별 지표 조회 및 일별 추이

관리팀은 전체 주문 수량을 본 다음 어느 모델의 어떤 색상·용량이 실적을 만들었는지 알고 싶어 했다. 고객이 보내온 목업은 모델 안에서 SKU별 주문량을 비교하는 화면과, 캠페인 첫날부터 날짜별 주문량을 따라가는 차트를 함께 보여줬다. 후속 대화에서는 날짜별 픽업량도 확인하고 싶다고 했다. *(고객 피드백표 F5:G5)*

요약에서는 상품별 실적을 살펴본다. 주문 수량·주문 금액·픽업 수량을 그룹별로 펼쳐 보고, 그룹을 누르면 SKU별 수치와 그 수치에 포함된 주문을 확인한다. 날짜에 따른 변화는 추이 탭에서 본다. 그룹 또는 SKU별로 주간 그래프를 보고, 지표를 바꿔 일별 주문 수량과 픽업 수량을 확인한다. 11월 17일 후속 답변에서 고객은 요약에는 세 지표 모두, 추이에는 두 수량 지표가 필요하다고 확인했다.

**화면에서 보기**

- [요약 · 그룹별 실적](https://saemishin.github.io/pre-order-phase3-wireframe/?scenario=P03#app-summary) — 캠페인 상세의 요약 탭에서 지표를 펼쳐 그룹별 수치를 확인하고, 원하는 그룹을 선택한다.
- [그룹 내 SKU별 수치](https://saemishin.github.io/pre-order-phase3-wireframe/?scenario=P03#app-sku-metrics) — 선택한 그룹의 총 합계와 SKU별 수치를 확인한다. 프리오더 수량·금액·픽업 수량을 전환할 수 있다.
- [SKU별 주문 목록](https://saemishin.github.io/pre-order-phase3-wireframe/?scenario=P03#app-order-list) — SKU를 선택하면 해당 SKU의 주문 목록으로 이동한다. 선택한 지표와 필터 조건에 맞는 주문을 기존 주문 카드로 확인한다.
- [일별 추이](https://saemishin.github.io/pre-order-phase3-wireframe/?scenario=P03#app-trend) — 일별 실적은 캠페인 상세의 추이 탭에서 확인한다. 프로덕트 그룹/SKU, 주문/픽업 수량, 조회 주간을 선택해 비교한다.

## P04-A · 일반 리더의 조회 권한 및 범위

리더가 실적을 보려면 어느 주문까지 그 리더의 실적으로 셀지 먼저 정해야 한다. 11월 17일 후속 확인에서 고객은 같은 매장에서 들어온 주문이라도 리더가 감독하지 않는 직원이 등록했다면 조회 대상에서 제외하는 데 동의했다.

일반 리더는 앱과 대시보드에서 관리 그룹과 하위 그룹 구성원이 등록한 주문을 본다. 목록·상세·다운로드·실적 합계에 같은 범위를 적용한다. 관리자와 별도 전체 조회 권한을 받은 리더는 기존 전체 조회 범위를 유지한다.

**화면에서 보기**

- [관리자 · 권한 설정](https://saemishin.github.io/pre-order-phase3-wireframe/?scenario=P04-A#permission-specific) — 관리자는 기존 설정에서 캠페인 생성 및 전체 조회 권한을 부여할 리더를 지정한다. 별도 권한이 없는 일반 리더도 담당 구성원 범위의 주문을 조회할 수 있다.
- [일반 리더 · 웹 캠페인 목록](https://saemishin.github.io/pre-order-phase3-wireframe/?scenario=P04-A#campaign-list-leader) — 일반 리더가 대시보드의 캠페인 목록에서 캠페인을 선택한다. 조회할 주문이 없어도 기존 캠페인 노출 조건에 맞으면 목록에 표시된다.
- [웹 캠페인 상세](https://saemishin.github.io/pre-order-phase3-wireframe/?scenario=P04-A#handraiser-detail?role=leader) — 캠페인 설정 정보를 조회하고, 담당 구성원의 주문 목록과 실적을 확인한다. 설정 수정과 Hand raiser 명단 관리 기능은 제공하지 않는다.
- [웹 주문 상세](https://saemishin.github.io/pre-order-phase3-wireframe/?scenario=P04-A#detail-leader) — 담당 구성원의 주문 상세를 연다. 전화번호·이메일 주소·신분증 번호와 더보기 메뉴는 표시되지 않는다.
- [앱 캠페인 목록](https://saemishin.github.io/pre-order-phase3-wireframe/?scenario=P04-A#app-campaigns?role=leader) — 앱 리더 모드에서도 캠페인 목록에 접근해 진행 중인 캠페인을 선택한다.

## P04 · 주문 상세 화면에서 고객 정보 비노출

고객은 리더가 현장에서 주문 내용을 확인할 때 고객의 전화번호·이메일·신분증 번호까지 볼 필요는 없다고 설명했다. 반면 별도 권한을 받은 리더가 웹 대시보드에서 업무를 처리할 때는 이 정보에 접근할 수 있어야 한다고 구분했다. *(고객 피드백표 F6:G6)*

앱 리더 모드에서는 관리자만 세 항목을 본다. 대시보드에서는 관리자와 별도 조회 권한 리더가 볼 수 있다. 일반 리더에게는 두 환경 모두 세 항목의 라벨과 값을 숨기고, 고객 이름과 그 밖의 주문 정보는 기존 기준대로 표시한다.

**화면에서 보기**

- [웹 주문 상세 · 고객 탭](https://saemishin.github.io/pre-order-phase3-wireframe/?scenario=P04#detail-leader) — 대시보드에서 주문 상세의 고객 탭을 연다. 관리자와 별도 조회 권한 리더는 전화번호·이메일 주소·신분증 번호를 볼 수 있고, 일반 리더에게는 해당 항목이 표시되지 않는다.
- [앱 주문 상세 · 고객 탭](https://saemishin.github.io/pre-order-phase3-wireframe/?scenario=P04#app-order-detail?role=leader) — 앱 리더 모드에서 주문 상세의 고객 탭을 연다. 관리자는 세 항목을 볼 수 있고, 별도 조회 권한 리더와 일반 리더에게는 표시되지 않는다.

## P05 · SKU별 주문 가능 근무지 설정

같은 유통사에 속한 매장은 재고를 함께 쓰지만 모든 매장이 같은 SKU를 취급하지는 않는다. 고객은 취급 매장을 제한하려고 매장별 수량까지 나누면 재고 이동과 주문 처리가 복잡해진다고 설명했다. 기대한 동작은 매장 A가 취급하지 않는 SKU가 그 매장의 주문 목록에 처음부터 뜨지 않는 것이었다. *(고객 피드백표 G7)*

관리자는 유통사 공통 재고를 유지하면서 SKU마다 주문 가능한 근무지를 지정한다. 앱은 주문 근무지에서 가능한 SKU만 보여준다. 대시보드 신규 일괄 등록도 같은 조합을 검사한다. 저장 전 오류가 있으면 저장을 막고, 저장 시점에 설정이 바뀌면 정상 주문은 등록하고 실패한 행만 표에 남긴다.

## P06 · Hand raiser 명단 업로드

캠페인 운영 중 대량의 사전 관심 고객(Hand Raiser) 이메일을 추가하고 잘못 올린 주소만 바로잡아야 한다. 고객은 잘못된 주소 여러 개를 일일이 지우는 부담을 줄여 달라고 요청했다. *(고객 피드백표 G8)*

관리자는 파일로 이메일을 추가하고, 주소를 정확히 검색해 여러 건을 선택 삭제한다. 이미 등록된 주소는 처리 성공에 포함하되 다시 추가하지 않는다. 실패한 주소만 같은 양식으로 내려받아 수정할 수 있다. 명단을 고쳐도 이미 완료된 주문의 판정은 유지한다.

**화면에서 보기**

- [생성·수정 · 명단 업로드](https://saemishin.github.io/pre-order-phase3-wireframe/?scenario=P06#handraiser-result) — 캠페인 생성·수정 시 이메일이 담긴 Excel 또는 CSV 파일을 업로드한다. 성공·실패 건수를 확인하고, 실패 건이 있으면 해당 파일을 내려받는다.
- [캠페인 상세 · 명단 현황](https://saemishin.github.io/pre-order-phase3-wireframe/?scenario=P06#handraiser-detail) — 캠페인 상세에서 등록된 이메일 수와 최근 업데이트 시각을 확인한다. 기존 명단은 실제 추가·삭제 후부터 시각을 표시하고, 명단이 0개이면 숨긴다.
- [이메일 관리](https://saemishin.github.io/pre-order-phase3-wireframe/?scenario=P06#handraiser-search) — 이메일 관리에서 주소를 검색한다. 정확히 일치하는 결과를 선택하고, 여러 번 검색해 선택한 이메일을 한 번에 삭제할 수 있다.
- [명단 추가 업로드](https://saemishin.github.io/pre-order-phase3-wireframe/?scenario=P06#handraiser-add) — 추가 업로드에서 파일을 올리고 성공·실패 건수를 확인한 뒤 저장한다. 성공한 이메일이 기존 명단에 추가되며 저장 완료 토스트가 표시된다.

## P07 · 주문별 Hand raiser 여부 수정

명단을 정리해도 이미 등록된 주문의 고객 이메일이나 Hand Raiser 판정을 바로잡아야 하는 경우가 남는다. 고객이 요청한 Hand Raiser 수정은 캠페인 명단 관리(P06)와 개별 주문 정정이라는 두 업무로 나눴다. 고객은 주문 이메일을 명단에서 확인하는 공유안에 이견이 없다고 답했다. *(고객 피드백표 G9)*

관리자는 개별 주문 수정에서 현재 입력한 이메일을 확인하고 Yes/No 결과를 저장한다. 확인 후 주소를 바꾸면 다시 확인해야 한다. 주소가 그대로면 그사이 명단이 바뀌어도 마지막 확인 결과를 저장한다. 여부가 실제 바뀌면 인보이스 재생성과 주문 이력에 반영한다. 일괄 수정은 기존 방식을 유지한다.

## P08 · 캠페인 목록에 진행 중 캠페인만 표시

리더에게 필요한 것은 지금 매장에서 진행 중인 캠페인이다. 고객은 리더의 목록에서 비활성·종료 캠페인을 덜어내되, 관리자는 이전 캠페인도 계속 조회할 수 있어야 한다고 요청했다. *(고객 피드백표 G10)*

## P09 · 픽업 기간일 때만 픽업 버튼 표시

고객은 보통 캠페인 하나를 2~3개 Batch로 운영한다고 설명했다. 첫 Batch는 이미 픽업을 시작했는데 다른 Batch는 아직 주문을 받는 날, 수령 버튼이 보인다는 이유로 어느 주문이든 픽업할 수 있는지 물었다. *(고객 피드백표 G11)*

직원 앱의 공통 수령 버튼은 회사 내 현재 픽업 가능한 Batch가 하나라도 있을 때 표시한다. 버튼을 눌러 주문을 조회한 뒤에는 그 주문이 속한 Batch의 기간을 다시 확인한다. 따라서 첫 Batch의 고객은 수령할 수 있고, 아직 픽업 기간이 오지 않은 Batch의 주문은 차단된다.

## P10-1 · 주문 완료 시 Batch 연결 보완

직원이 주문을 시작할 때와 완료할 때 사이에 Batch 기간이 바뀔 수 있다. 저장된 Batch가 맞지 않으면 주문 상세와 인보이스가 안내하는 픽업 기간까지 어긋날 수 있어 운영 보완 항목으로 정리했다.

서버는 주문 완료 시 선택한 Batch가 유효하면 그대로 저장한다. 기간이 끝났다면 다음 순서 중 현재 유효한 가장 가까운 Batch를 연결하고, 그런 후보가 없으면 기존 선택을 유지한다. 주문과 픽업 기간 안내는 최종 연결 결과를 따른다.

## P10-2 · 픽업 입력 단계의 기기 식별정보 중복 검증 보완

픽업 마지막 단계에서 기기 번호 중복이 드러나면 직원은 서명까지 받은 뒤 입력 단계로 돌아가야 한다. 운영 검토에서는 잘못된 번호를 입력한 자리에서 확인할 수 있게 하는 데 초점을 뒀다.

직원이 IMEI 또는 S/N을 입력하고 다음 단계로 갈 때 중복을 검사한다. 수정한 값은 다시 검사하고 최종 완료 때도 중복 여부를 확인한다. 마지막에 오류가 발견돼도 다른 입력과 서명은 유지한다.

## P10-3 · 주문 완료 시 MBO 확인 보완

결합 구매 할인(MBO)을 확인한 뒤 주문을 마치기까지 날짜가 바뀌거나 할인 기준이 된 주문이 변경될 수 있다. 운영상 구분할 것은 날짜만 넘어간 경우와 실제 구매 조건이 달라진 경우다.

유효한 임시 주문에 반영된 할인은 날짜가 바뀌어도 유지한다. 완료 시 실제 구매 조건을 확인해 할인 결과나 금액이 바뀌면 갱신한 금액을 직원에게 보여준다. 직원이 다시 완료를 눌러 확인한 뒤 주문을 저장한다.

**화면에서 보기**

- [결제 정보 · MBO 재확인](https://saemishin.github.io/pre-order-phase3-wireframe/?scenario=P10-3#app-employee-last) — 결제 정보 화면에서 완료를 누른다. 최종 MBO 확인 결과가 바뀌면 같은 화면의 가격·할인이 갱신되고 “가격 정보가 변경되었습니다.” 토스트가 표시된다. 변경된 금액을 확인한 뒤 완료를 다시 누른다.
