# 주문 및 픽업 처리

## 1. 주문 완료 시 Batch 연결

### 1-1. 적용 범위·판정 시점

- Android 앱 신규 주문의 최종 저장 시 서버가 연결할 Batch를 결정한다.
- 사용자가 주문을 시작할 때 선택한 Batch를 기준으로, 서버의 최종 저장 시점에 해당 Batch의 주문 기간이 유효한지 판단한다. 픽업 기간으로 판단하지 않는다.
- 주문 일시와 Batch 판정에는 동일한 기준 시각을 사용한다.
- 신규 주문을 시작할 수 있는 기간과 기존 Batch 선택 동작은 변경하지 않는다.

### 1-2. 최종 Batch 결정 기준

| 완료 시점의 조건 | 최종 연결 기준 |
| --- | --- |
| 선택한 Batch가 주문 기간 내임 | 처음 선택한 Batch를 유지한다. 다른 유효 Batch가 동시에 있어도 변경하지 않는다. |
| 선택한 Batch의 주문 기간이 종료됐고 유효한 후순위 Batch가 있음 | 해당 주문에 적용 가능한 후순위 후보 중 가장 가까운 다음 순서의 Batch를 적용한다. |
| 바로 다음 순서의 Batch가 유효하지 않음 | 해당 Batch를 건너뛰고 유효한 후순위 후보 중 가장 작은 순서를 적용한다. |
| 유효한 후순위 Batch가 없음 | 기존 선택 Batch를 유지하여 주문을 완료한다. 유효한 Batch가 전혀 없거나 앞번호 Batch만 유효한 경우를 모두 포함하며, 앞번호로 자동 이동하지 않는다. |

- 후보는 동일 캠페인에서 주문 기간과 해당 주문의 근무지·사용자 등 기존 대상 조건을 충족하는 Batch로 제한한다. 기간만으로 임의의 Batch를 연결하지 않는다.
- 다음 순서는 시작일이나 제목 문자열이 아니라 설정된 Batch 순서(`idx`)를 기준으로 한다.
- 유효한 후순위 후보가 없어 기존 선택을 유지하는 경우에는 주문 일시가 해당 Batch의 주문 기간 이후일 수 있다. Batch 기간 종료만으로 진행 중 주문의 완료를 차단하지 않기 위한 예외다.

### 1-3. 기존 검증·저장 결과

- 기존 재고·인증·필수값·임시 주문의 재고 확보 만료 등 다른 완료 검증은 유지한다.
- [주문 가능 근무지 검증](Policy_04_Product_및_Allocation.md#8-주문에-적용하는-기준)도 별도로 적용한다. Batch 연결의 예외 처리로 다른 검증 실패를 통과시키지 않는다.
- 저장하는 Batch ID와 관련 Batch 정보를 최종 결정 결과로 일치시킨다. 완료 응답·주문 상세·인보이스가 참조하는 Batch 및 픽업 기간도 같은 결과를 사용한다.
- 이미 완료된 주문이나 과거 오류 주문의 소급 보정, 대시보드 과거 주문 등록·일괄 업로드는 이 변경에 포함하지 않는다.

## 2. 주문 완료 시 MBO 확인

### 2-1. 적용 범위·혜택 보장 기준

- Android 앱에서 진행 중인 신규 주문의 최종 완료 시 MBO 적용 여부와 금액을 다시 확인한다. 1/2 단계에서 확인한 결과만으로 최종 확인을 생략하지 않는다.
- 서버가 임시 주문을 생성하면서 정상 반영한 MBO 혜택을 보장 기준으로 삼는다.
- 해당 임시 주문이 유효한 동안 날짜가 바뀌었다는 이유만으로 기존 MBO 할인을 취소하지 않는다. 날짜 경과와 실제 구매 조건의 소멸을 구분한다.
- 기존 임시 주문의 재고 확보 유효시간(생성 후 30분)을 유지한다. MBO 재확인이나 금액 변경으로 유효시간을 연장하거나 만료 시각을 다시 설정하지 않는다.
- 만료 후 새 주문을 시작하면 새 시점의 기존 MBO 판정 조건을 적용한다. 만료된 임시 주문의 혜택을 새 주문으로 이월하지 않는다.

### 2-2. 최종 판정 기준

| 조건 | 처리 기준 |
| --- | --- |
| 기존 MBO 적용 상태에서 날짜만 바뀜 | 임시 주문의 유효시간 안에서는 기존 혜택을 유지한다. |
| 기존 MBO 미적용 상태 | 완료 시 추가 적용 가능한 MBO가 있는지 확인하고 판정 결과를 반영한다. |
| 기준 주문 삭제·상품 변경 등으로 실제 구매 조건이 사라짐 | MBO를 다시 판정한다. 다른 유효한 기준 구매가 있으면 해당 구매를 포함한 판정 결과를 사용한다. 기준 주문 하나의 삭제만으로 무조건 미적용 처리하지 않는다. |

- 날짜 경과에 따른 혜택 보장과 실제 구매 조건 확인을 구분해 적용한다. 현재 날짜 기준의 조건을 일괄 재실행하여 보장된 혜택을 취소하지 않는다.

### 2-3. 결과 변경·최종 저장

- 최종 판정한 MBO 결과 또는 적용 금액이 사용자에게 표시된 결과와 다르면 해당 요청에서는 주문을 완료·저장하지 않는다. 변경 결과를 반영하고 사용자의 재확인 후 완료한다.
- 사용자가 다시 완료를 요청하면 최신 결과를 다시 확인한다. 현재 표시된 결과와 같고 다른 완료 조건도 충족하면 저장한다. 다시 달라졌다면 변경 결과를 반영하고 재확인을 받는다.
- 재확인 과정에서 진행 중 주문의 입력값과 첨부파일을 유지한다. 구체적인 금액 표시·토스트·버튼 동작은 [주문 진행 2/2 화면](../description/App(E)_dc_01_주문_진행.md#3-주문-진행-22--결제-정보-화면)을 따른다.
- 최종 저장하는 MBO 여부·할인·금액과 주문 완료 결과·최초 인보이스가 사용하는 정보를 일치시킨다.
- 기존 재고·인증·필수값·임시 주문 유효시간·주문 가능 근무지 등 다른 완료 검증은 유지한다.
- 이미 완료된 주문의 혜택을 소급 재판정하거나 자동 수정하지 않는다.

## 3. 픽업 기간과 진입 가능 여부

### 3-1. 공통 수령 진입의 판단 범위

- Android 직원 모드 Pre-order 캠페인·Batch 목록의 공통 수령 진입에 적용한다.
- 기존처럼 회사 전체 Batch를 기준으로 판단한다. 해당 직원에게 배정된 Batch만으로 판단 범위를 좁히지 않는다.
- 미삭제·확정 캠페인의 미삭제 Batch를 대상으로 하는 기존 조건과 앱 목록 항목 존재 조건을 유지한다.
- 위 조건을 충족하면서 현재 시각이 픽업 가능 기간에 포함되는 Batch가 하나 이상 있어야 수령 진입을 제공한다. 여러 Batch 중 하나만 픽업 기간 안이어도 기간 조건을 충족한다.
- 직원 모드 캠페인·Batch 목록 자체의 조회 범위나 정렬은 변경하지 않는다.

### 3-2. 기간 판정

| 현재 시각과 Batch 픽업 기간 | 기간 조건 충족 여부 |
| --- | --- |
| 픽업 시작일시 전 | 충족하지 않는다. |
| 픽업 시작일시 이상이며 종료일시 이하 | 충족한다. 시작·종료 경계를 포함한다. |
| 픽업 종료일시 후 | 충족하지 않는다. |
| 종료일시가 없고 시작일시 이상 | 충족한다. 기존 종료일 미설정 처리를 유지한다. |
| 시작일시가 없음 | 충족하지 않는다. |

- 주문 기간이나 캠페인의 진행 중 상태로 픽업 기간을 대신 판단하지 않는다.
- 시각·시간대와 경계 처리는 기존 주문 조회·픽업 완료의 픽업 가능 여부 판정과 일치시킨다.
- 별도 자동 갱신·타이머 기능을 추가하지 않고 기존 조회·갱신 시점에 변경된 기간 조건을 적용한다.

### 3-3. 주문별 픽업 허용 기준

- 공통 수령 진입이 가능하더라도 실제 주문 조회와 픽업 완료 시에는 해당 주문이 속한 Batch의 픽업 기간을 각각 확인한다.
- 다른 Batch가 픽업 기간 안이라는 이유로 해당 주문의 기간 밖 픽업을 허용하지 않는다.
- 진행 중 해당 주문의 픽업 기간이 종료되면 기존 최종 검증으로 완료를 차단한다.
- 기존 주문별 기간 검증·차단 동작과 안내 문구를 유지한다. 기간 밖 픽업 허용이나 안내 문구 개선은 이번 변경에 포함하지 않는다.
- 구체적인 버튼·안내 표시는 [직원 모드 픽업 화면](../description/App(E)_dc_02_픽업_진행.md)을 따른다.

## 4. 픽업 기기 식별정보 중복 검증

### 4-1. 대상과 비교 범위

- Android 픽업 입력 단계에서 사용하는 IMEI 1·IMEI 2·S/N을 대상으로 한다. 상품 카테고리 설정에 따른 기존 항목 노출·필수 여부를 유지한다.
- 같은 회사·캠페인·상품 카테고리의 미삭제 픽업 완료 주문(DONE)에 등록된 값과 비교한다. 상품 카테고리는 프로덕트 그룹과 구분한다.
- Batch·근무지·유통사별로 중복 비교 범위를 분리하지 않는다.
- 입력값은 비교 대상 주문의 IMEI 1·IMEI 2·S/N 전체와 교차 비교한다. 같은 이름의 필드끼리만 비교하지 않는다.
- 현재 주문은 다른 주문과의 중복 비교 대상에서 제외한다. 비필수 항목을 비워 둔 경우 기존 허용 기준을 유지한다.

### 4-2. 검증 시점과 비교값

- 기기 정보 입력 단계에서 다음 단계로 진행할 때 서버 기준의 중복 검증을 추가한다. 최종 완료 단계에 도달하기 전에 중복값을 확인할 수 있어야 한다.
- 입력값을 직접 수정하거나 스캔으로 바꾼 뒤에는 변경된 값으로 다시 검증한다. 이전 값이 검증을 통과했다는 이유로 새 값의 검증을 생략하지 않는다.
- 입력값과 기존 저장값을 비교할 때 동일한 정규화 기준을 적용한다. IMEI의 숫자 처리, S/N의 공백·대소문자 처리 등 기존 정규화 기준과 일치시켜 표현 차이로 중복 검증이 누락되지 않도록 한다.
- 기존 필수값·형식·상품 정보 일치 등 다른 검증은 유지한다.

### 4-3. 검증 결과와 최종 완료

- 입력 단계에서 중복이 확인되면 다음 단계로 진행하지 않는다. 중복된 항목을 식별할 수 있도록 결과를 반환하고, 사용자가 값을 수정한 뒤 다시 진행하도록 한다.
- 입력 단계에서 통과해도 최종 픽업 완료 시 기존 서버 중복 검증을 유지한다. 입력 단계 통과 후 다른 주문에서 같은 번호가 등록되는 경우도 최종 검증 대상이다.
- 최종 중복으로 차단되면 픽업을 완료하지 않는다. 기존처럼 기기 정보 입력 단계로 돌아가 중복 항목을 수정하도록 하며 다른 입력값과 서명을 유지한다.
- 기존 중복 오류 문구와 필드별 오류 표시를 사용한다. 구체적인 오류 해제·버튼 동작은 [직원 모드 픽업 화면](../description/App(E)_dc_02_픽업_진행.md#3-기기-정보-입력-12-화면)을 따른다.
- 동일 주문의 IMEI 1·2 동일값 검사를 다른 검증 설정과 독립적으로 실행하도록 보완하는 작업은 이번 추가 범위에 포함하지 않는다. 기존 검사를 제거하거나 허용 기준을 변경하지 않는다.

## 5. 신규 등록과 기존 주문 수정의 근무지 검증 범위

- Android 신규 주문과 대시보드 신규·일괄 등록에는 [주문 가능 근무지 정책](Policy_04_Product_및_Allocation.md#8-주문에-적용하는-기준)을 적용한다. 앱의 다음·완료와 대시보드 파일 적용·값 수정·최종 저장의 검증 시점은 해당 정책을 따른다.
- 주문 근무지를 사용하지 않는 온라인 주문은 근무지 제한 검증에서 제외하되, 기존 온라인 주문 검증은 유지한다.
- 이미 완료된 주문은 이후 주문 가능 근무지 설정 변경으로 취소·수정하지 않는다. 관리자 개별·일괄 주문 수정에도 이 검증을 추가하지 않는다.
- 기존 주문 수정의 Hand Raiser 검증은 근무지 제한과 별개이며 [Hand Raiser 정책](Policy_05_Hand_raiser.md#6-기존-주문의-hand-raiser-여부-수정)을 따른다. 일괄 수정은 명단 검증을 추가하지 않고 이메일·Yes/No 직접 변경과 인보이스 처리를 현행 유지한다. 세부 기준은 같은 정책의 8절을 따른다.
