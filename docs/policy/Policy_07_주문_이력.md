# 주문 이력

주문에서 발생한 생성·정보 수정·픽업·삭제·복구·인보이스 재생성 작업을 기록한다. 이력은 대시보드의 주문 상세에서 관리자에게 제공한다.

## 1. 기록 시점과 단위

| 작업 | 기록 기준 | 함께 남길 정보 |
| --- | --- | --- |
| 주문 생성 | 임시 주문이 아닌 주문 완료 시 한 건 | 주문 생성자·생성 당시 주문일시·작업 처리 시각 |
| 정보 수정 | 실제 변경된 항목마다 한 건. 개별·일괄 수정 모두 동일 | 항목명·변경 전값·변경 후값·수정자·수정일시 |
| 픽업 | 최초 픽업 완료 시 한 건 | 픽업 담당자·처리 시각 |
| 삭제 | 주문 삭제 시 한 건 | 수행자·처리 시각 |
| 복구 | 주문 복구 시 한 건 | 수행자·처리 시각 |
| 인보이스 재생성 | 최초 발행 이후 새 PDF 생성에 성공할 때마다 한 건 | 수행자·처리 시각 |

- 주문 생성·최초 픽업에서 함께 저장하는 최초 입력값은 별도 항목 수정 이력으로 중복 기록하지 않는다.
- 여러 항목을 한 번에 저장해도 바뀐 항목별로 각각 기록한다. 같은 저장에서 생성된 수정 이력은 같은 수정자·수정일시를 사용한다.
- 변경되지 않은 항목은 기록하지 않는다. 저장 전에 입력을 바꿨다가 원래 값으로 되돌린 경우에도 최종 변경이 없으면 수정 이력을 만들지 않는다.
- 기존 주문의 주문일시·주문 생성자를 나중에 정정해도 과거 생성 이력을 덮어쓰지 않는다.
- 삭제·복구는 각 작업 한 건으로 기록한다. 삭제 여부·삭제자·삭제일시를 각각 수정 이력으로 나누지 않는다.
- 복구 시 기존 값을 되살리는 것을 항목별 ‘없음 → 값’ 수정으로 기록하지 않는다.
- 삭제된 주문 조회·사용자 복구 기능은 이번 범위에 추가하지 않는다. 기록은 보존하며 향후 복구된 주문에서 기존 이력을 이어 조회할 수 있어야 한다.

## 2. 직접 수정과 연동 변경

- 주문의 업무 정보를 직접 변경하면 화면·DB 보정 경로와 관계없이 아래 기록 대상 기준을 적용한다.
- 다른 항목 수정으로 따라 바뀐 계산값·연동값은 별도 수정 이력으로 만들지 않는다. SKU 변경으로 금액이 재계산되는 경우에는 주문 상품 변경만 기록한다.
- 마스터 정보 자체의 명칭·가격·속성 변경은 개별 주문 이력에 기록하지 않는다. 주문 저장 시 최신 마스터값이 반영되는 경우도 별도 수정 이력을 만들지 않는다.
- 내부 식별자·인보이스 생성 상태 등 내부 처리값·공유 재고 집계의 변화는 사용자용 주문 수정 이력에서 제외한다. 업무 정보인 주문 상태를 직접 정정한 경우는 아래 항목별 기준에 따라 기록한다.
- 인보이스 재생성은 연동 변경 제외 원칙의 예외다. 자동으로 실행돼도 성공한 재생성 작업을 기록한다.
- 기록 대상이라는 이유로 기존에 불가능한 화면 수정을 새로 허용하지 않는다.

## 3. 상품과 첨부파일

- 프로덕트 그룹과 SKU는 ‘주문 상품’ 변경 한 건으로 기록한다. 변경 전후 각각의 프로덕트 그룹과 SKU를 함께 기록한다. 같은 그룹 안에서 SKU만 바뀌어도 동일하다.
- 고객 정보·결제 증빙·Trade-in 첨부파일은 추가와 삭제를 기록한다. 파일 교체 유형·파일 내용 비교·별도 사본 보관을 추가하지 않는다.
- 내부 파일 경로나 관계 레코드만 다시 생성된 경우에는 첨부파일 변경 이력을 만들지 않는다.
- 첨부파일 이력의 조회 범위는 파일명으로 한정한다. 이력을 통한 원본 파일 열람·다운로드는 제공하지 않는다.

## 4. 인보이스 재생성

- 주문 완료 시 최초 인보이스 발행은 생성 작업에 포함하며 별도 재생성 이력을 만들지 않는다.
- 이후 수동·자동 실행 여부와 관계없이 새 PDF 생성에 성공할 때마다 재생성 작업 한 건을 기록한다. PDF 내용이 같거나 파일 경로가 같아도 동일하다.
- 정보 수정과 재생성이 함께 발생하면 항목별 수정 이력과 재생성 이력을 각각 기록한다.
- 직접 재생성은 실행자, 정보 수정에 따른 자동 재생성은 수정을 실행한 사용자를 수행자로 기록한다. DB 보정 경로는 Shopl 운영 계정을 적용한다.
- 실패 시도, 단순 열람·다운로드는 재생성 이력으로 기록하지 않는다.
- 과거 PDF 버전 열람·별도 사본 저장·재발송 이력은 이 정책으로 추가하지 않는다.

## 5. 수행자와 표시값 보존

- 모든 이력에 수행자와 작업 처리 시각을 남긴다.
- 항목명·변경 전후 표시값·수행자 이름은 이력 생성 당시의 값을 보존한다. 이후 이름·마스터 변경이나 삭제로 과거 이력 표시를 다시 쓰지 않는다.
- 사용자 정의 항목은 각각의 항목 단위로 기록하며 당시 항목명과 전후 값을 보존한다.
- 과거 변경 전값에 고객 정보가 남을 수 있다. 보관·처리는 기존 주문 데이터의 기준을 따른다.

## 6. DB 보정

- 표준 보정 스크립트를 통해 주문 변경과 이력을 같은 트랜잭션으로 저장한다.
- 수정자는 실제 담당자의 개인 계정이 아닌 Shopl 운영 계정으로 기록하고 실제 보정 시각을 사용한다.
- 모든 임의 SQL을 자동 감시하는 기능을 의미하지 않는다. 정해진 보정 경로에서 이력을 보장한다.
- 사용자 수정 불가 여부와 DB 보정 기록 여부는 별도로 판단한다. 주문 ID·주문 코드 등 고유 식별값의 변경을 정상 보정으로 허용하지 않는다.

## 7. 적용·조회·보관

- 기능 적용 이후 발생한 작업부터 기록한다. 기존 주문도 적용 이후 작업은 기록하지만 적용 이전 사건은 소급 생성하지 않는다.
- 대시보드에서 관리자 계열(ADMIN·SUPER_ADMIN·OPERATOR)만 이력을 조회한다. 리더는 별도 pre-order 조회 권한이 있어도 이력을 조회하지 못한다. 기존 주문 조회 가능 범위 안에서 제공하며 앱 이력 조회는 제공하지 않는다.
- 보관 기간은 기존 주문 데이터의 보관 기간에 맞춘다. 서비스에서 주문을 삭제해도 기존 이력은 보존한다.
- 신규 개인정보 파기 화면이나 기능을 추가하지 않는다.

## 8. 항목별 기록 기준

사용자 직접 수정은 화면에서의 수정 가능 여부와 기록 기준이다. DB 직접 보정은 업무값 자체를 직접 보정했을 때의 기준이다. 연동 변경의 ‘기록 안 함’은 이력 기준이며 해당 자동 변경 기능의 제공 여부를 뜻하지 않는다.

- 주문별 Hand raiser 여부는 실제 저장 성공 후 값이 바뀌면 기록한다. 개별 수정은 이메일 확인 결과를 반영하며, 일괄 수정은 명단 검증 없이 Yes/No를 직접 변경하는 현행 방식을 유지한다. 일괄 수정의 인보이스 재생성 조건은 변경하지 않되, 실제 변경과 기존 조건에 따른 재생성 성공은 이 정책에 따라 기록한다. 명단 업로드로 기존 주문 여부를 소급 갱신하지 않는다.
- 주문 생성자와 주문일시는 수정 가능 여부가 달라 표에서 구분하지만, 최초 생성은 한 건의 이력이다.
- 픽업 담당자는 DB에서 직접 보정하면 기록한다. 일괄 수정의 부수적 담당자 변경은 연동 변경 기준을 따른다.
